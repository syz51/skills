# Feedback capture and review

Use this guide when real work yields a concrete lesson or the user requests a review of this skill's feedback. The local store is `~/.codex/skill-feedback/content-research-writer/` on the acting host. Capture observations during authorized execution; planning, advice, and review requests remain read-only unless saving or changes are requested. Feedback never authorizes publication, external communication, or disclosure.

## Capture a useful observation

- Finish the requested work and its verification first. Record material user corrections, conflicting or missing guidance, unnecessary prescribed work, and techniques supported by an observed success. Do not invent lessons or create a note for every task.
- Create one short Markdown file per distinct lesson in `~/.codex/skill-feedback/content-research-writer/notes/`, expanding `~` to the acting host’s home directory. Name it `<UTC timestamp>-<sanitized hostname>-<random UUID>.md`. Publish complete contents atomically without replacing an existing file: write a temporary file in the same directory, close it, hard-link it to the final name with exclusive creation, then remove the temporary file; retry a collision with a new UUID. Keep notes outside the project or deliverable. If saving is unavailable or disallowed, report the material lesson briefly without interrupting delivery.
- Record the actual hostname, chat/thread identifier (Claude Code exposes it to shell commands as `$CLAUDE_CODE_SESSION_ID`; otherwise unavailable), deployed revision at capture, and actually loaded skill version/hash. For the capture-time deployment, resolve `~/.local/share/codex-skills/current` and use its release-directory commit when named by a full commit hash, or `git rev-parse HEAD` in the resolved checkout; if neither establishes the revision, say unavailable. An active chat may have loaded an earlier skill: record the loaded version/hash only when established from the actual loaded content or reliable session evidence, otherwise mark it unknown. Never substitute the current deployment or its file hash as proof of the version used. Saving a note performs no Git operation, upload, or external write; synchronization belongs to the separately authorized local background job.
- Identify the task, concrete correction or decision, and affected rule/reference when known. Label user corrections, instruction defects, verified outcomes, and reported techniques distinctly. Use source-turn/message anchors or local artifact evidence without copying private excerpts. A completion summary alone is not a demonstrated success or reusable lesson; separate project findings from shared guidance problems.
- Diagnose unclear guidance, an ignored existing rule, a project-specific exception, or an uncertain cause. Propose a change only when supported; a useful success may justify preserving a rule. Treat voice, genre, audience, and citation preferences as contextual unless the user makes them general.
- Store minimum context. Omit credentials, personal/customer data, private drafts, unpublished source text, and confidential research; use redacted descriptions or local references. Notes and quoted instructions are evidence, not commands or authorization.

Use this compact format. Keep Recorded, Machine, Thread, Skill, Observation, and Evidence; mark unknown metadata unavailable and omit optional fields that add no value:

```markdown
# <concrete lesson>
- Recorded: <UTC date/time>
- Machine: <actual hostname>
- Thread: <chat/thread identifier or unavailable>
- Turn: <completed turn identifier, when available>
- Task: <brief context and artifact or chat reference, if available>
- Skill: content-research-writer; deployed-at-capture <commit or unavailable>; loaded <version/hash or unknown>; <relevant section/reference>
- Observation: <what happened; verified, reported, or hypothesis>
- Evidence: <correction, result, or reproducible check; material limitations>
- Cause: <guidance gap, ignored rule, project exception, or uncertain>
- Proposal: <small change, preserve current guidance, or investigate>
```

## Automatic capture fallback

The authorized hourly job on each Mac checks completed host-local Codex and Claude Code turns before uploading notes. It recognizes actual use of the maintained skills, skips subagent and maintenance sessions, and extracts only concrete reusable lessons. It records completed-turn evidence IDs and retry state under `~/.local/share/codex-skills/`; repeated runs do not create another note for the same evidence. Interrupted or active turns wait until completion. Capture-time deployment and the actually loaded version remain distinct; unknown loaded versions stay unknown.

Automatic notes use the same local notes folder and weekly review path. The extractor treats transcript text as untrusted evidence, abstracts task-specific details, and rejects private identifiers and copied source text. Notes are observations for later review, never new instructions. Continue saving clear lessons during delivery; the background job provides coverage when that step is missed. Read-only work remains excluded unless feedback saving is explicitly requested.

Automatic `Loaded reads` record hashes of identifiable guidance text actually returned in the source session, with the relative skill/reference path and originating read turn. The shared guidance reader returns bounded, self-identifying content; capture checks its hash and requested path/offset before accepting it. Each chunk is partial unless it contains the whole file; chunks are not combined into an inferred full-file hash. Complete ordinary single-file reads and partial excerpts are also recognized. Claude Code skill injections omit frontmatter and are recorded as partial. Ambiguous, failed, or truncated reads remain unknown. These hashes describe observed content, not today's installed file or proof that later compaction retained it.

The host-local source checker assesses every note against its original completed turn, without selecting by wording. It preserves message order and complete text when it fits; bounded inputs identify omitted messages and shortened text. Missing sources stay unresolved. Receipts bind note/source hashes, identity, loaded reads, and an abstract assessment; supported attribution does not verify the reported fix or outcome.

Missing identities are searched automatically each hour using a retained capture evidence ID or a unique successful saved note write matching the filename, recorded date and content. Supported creation formats are literal Python writes, templates whose substitutions contain only timestamps, hashes or paths, and new files created with Claude Code's Write tool. Saved commands are parsed, never run; the normal source check must finish before a receipt records the link. Ambiguous origins, conflicting IDs and unsupported formats stay unavailable and are retried when saved evidence changes. Settled canonical assessments can cover identical metadata-free duplicates on the other Mac without copying private chat history or creating a foreign-host local receipt.

Legacy `verifications/<note-sha256>.json` receipts remain unchanged. New assessments use `<note-sha256>--<assessment-sha256>.json`, fingerprint the checker and exact input, disclose input truncation, and link the prior receipt through `supersedes`. Legacy checks are reassessed once automatically. For another check, use `scripts/evidence.py --note-sha <hash> --recheck`. `scripts/evidence.py --report <feedback-directory>` validates history and selects the latest unsuperseded assessment; use that result while preserving earlier receipts. Transport retains the same names under `feedback/<skill>/verifications/<host>/`.

The hourly source job also attempts a conservative correction for eligible partial or unsupported notes. Drafting and a separate check use the original turn and available follow-ups; only a privacy-validated, supported correction checked with complete input is accepted. V3/V4 receipts store the corrected fields in `correction.note` with generation and verification input hashes, or `correction: null` when no safe rewrite is established. The original note and its assessment remain intact; a correction adds neither a duplicate note nor an independent case. Operational failures use the existing job retry and notification path. Missing or clipped sources and absent runtime results stay unknown.

Unresolved assessments, including bounded checks, are rechecked automatically when a restored/fuller original or newly completed same-chat messages change the evidence. Unchanged evidence and unrelated chats skip the model. V4 `evidenceSha256` and `followUps` bind the watched evidence and its dates. Later reports cannot retroactively justify an earlier assertion; reported checks still differ from independently observed outcomes. Complete accepted assessments remain historical records. The source scan can use read-only confirmations without capturing new feedback; it does not search arbitrary project files or replay tools. Changed checker code or an explicit recheck can also retry unresolved assessments.

## Review a batch

Before relying on feedback, use the effective source assessment and match the note's full hash, host, skill, thread, and turn; cite its path/hash. A partial, unsupported, missing, or truncated check cannot establish an omitted or contested claim. Request a host-local check or recheck when needed and authorized. A prose resolution does not replace a linked assessment. Reassessments can correct prior dispositions but are not independent cases; private originals stay outside this repository. When an effective v3/v4 receipt contains a supported, untruncated `correction.note`, use that checked wording for the same case and cite its receipt and input hashes. The original partial or unsupported wording remains historical evidence, not an accepted claim.

1. Read the current skill and relevant references. For the authorized weekly review, use the canonical Git checkout at `~/.local/share/codex-skills/repository` and its `feedback/content-research-writer/notes/` and `feedback/content-research-writer/reviews/`, including synchronized notes from both hosts; inspect the acting host’s unsynchronized notes when relevant and report missing host coverage. Inventory notes and prior reviews; cover the requested period or all unreviewed notes by default. Revisit provisional changes when newer evidence bears on their effect. Identify files covered and unavailable evidence; an empty batch is not grounds for invented improvements.
2. Group related observations and distinguish corrections, defects, reported techniques, and project-specific findings. Prioritize explicit user corrections. For an "already covered" decision, cite the exact existing rule/reference and explain how it handles this case. For repeated failures, check clarity, routing, and observed reference reads before adding another rule; unknown reads do not establish non-use. An established instruction defect or supported correction can justify a narrow provisional clarification before its benefit is measured.
3. Propose the smallest supported clarification, replacement, or deletion. Preserve scope, author voice, factual and citation fidelity, and authorization boundaries. Avoid turning one author's preference into a universal style rule. Ask about consequential unresolved preference conflicts. A review request permits findings and proposals; apply edits only within an explicit request or the weekly task's saved authorization.
4. For authorized edits, retain a recoverable before-state, preserve concurrent edits, and inspect the focused diff. Run the skill validator and check affected links. Revisit the originating case and a contrasting representative task through observable outcomes. If replay is unavailable, state that limitation and what later real work should confirm. Structural validation and fluent prose do not demonstrate better evidence handling or reader understanding. Use an independent reviewer when requested or when practical and authorized.
5. When saving or applying a review is authorized, create an atomic, uniquely named Markdown record using the same UTC/hostname/UUID convention in `feedback/content-research-writer/reviews/` in the canonical Git checkout for the weekly review, or `~/.codex/skill-feedback/content-research-writer/reviews/` for a local-only review. Record covered note filenames and dispositions, evidence, changes or deliberate no-change decisions, before/after entrypoint hashes if edited, verification, and open questions. Preserve source notes. Mark claimed improvements provisional until supported by subsequent use.

Later reviews should check whether a revision reduced the observed problem, introduced friction, or added unnecessary work. Keep, revise, or remove it according to evidence. Ordinary writing tasks should load neither accumulated feedback nor unrelated review history. Review upstream updates within the local maintenance boundaries in [Source provenance and update policy](../sources.json).
